Introduction

なぜいま、AI戦略を「再整理」する必要があるのか

Microsoft 365 Copilot は社内生産性AIとして急速に普及した。
一方で、PoCが本番化しない・顧客対応で活かせない・ROIが見えない、という声も多い。
これはベンダ選定の問題ではなく、設計論の問題である。

Microsoft 365 Copilot は、Fortune 500 の nearly 70% で利用されている1。さらに Microsoft Copilot Studio 上では over 400,000 のカスタムエージェントが作成され1、社内生産性領域における AI の浸透は明確に進んでいる。Microsoft Graph 経由で社員の email / chat / document / meeting を文脈化する仕組み2は、すでに多くの企業の日常業務に組み込まれている。

その一方で、現場で繰り返し聞かれる声がある。「PoC は走るが本番化しない」「Copilot は社内では使えるが、顧客対応では使えていない」「AI への投資 ROI が経営層から見えない」——。これらの課題は、より高性能なモデルや新しいベンダを選べば解決するわけではない。「どの AI を、どの業務レイヤーに置くか」という設計の問題だ。

本書は、AI 戦略を 「社内生産性 AI」と「顧客接点 AI」という二層モデルで再整理する。Microsoft 365 / Copilot を中心に AI 投資を進めてきた企業が、次の一手として顧客接点・収益業務の AI をどう設計すべきかを、製品の優劣ではなく設計原則として提示する。

本書のスタンス
本書は Microsoft を否定しない。Microsoft 365 / Copilot / Microsoft Graph / Copilot Studio / Microsoft Fabric / OneLake / Microsoft Purview / Microsoft Entra ID は、社内生産性AIの強力な基盤であり、本書はそれぞれを「強い領域」として肯定的に位置づける。一方で、顧客接点・収益業務に踏み込む AI には別の設計論が必要だ——という二層モデルを提示する。

日本の文脈では、IPA「DX動向 2025」が示すテーマ「内向き・部分最適から外向き・全体最適へ」3とも通じる。社内効率化で止まらず、顧客接点・収益業務まで AI 投資を伸ばすには、二層モデルで設計を整理する必要がある——というのが本書の出発点だ。

社内生産性AIと顧客接点AIは、
何が違うのか

「Copilot で全社業務が AI 化できるはず」——この前提を、データ・KPI・リスク・責任分界点という8つの観点で点検する。違いは、ベンダの優劣ではなく設計目的の違いにある。

社内生産性AIと顧客接点AIは、扱うデータも、主ユーザーも、失敗時の影響も、KPIも、責任分界点も異なる。同じ「AI」と呼ばれているからといって、同じ設計で実装できるとは限らない。本章では、まず両者の違いを8観点で並べる。

Microsoft 365 Copilot の役割は、社内生産性AIとして極めて明確
Microsoft 365 Copilot は、Microsoft Graph 経由で "a user's emails, chats, documents, and meetings" を文脈化する2。これは社員の日常業務に強く効く設計であり、本書はこの強みを否定しない。本書が論じるのは、その先にある「顧客接点AI」の設計だ。

AI戦略で見落とされやすい3つの盲点

盲点①：成果はモデル性能ではなく「データ」で決まる
LLM の性能競争が話題の中心になりがちだが、顧客接点AIの成果は、AI が参照する顧客接点データの質と業務プロセスへの組み込み深さで決まる。同じモデルでも、商談履歴・ケース履歴・契約・同意がリアルタイムに参照できるかで結果は大きく変わる。
盲点②：汎用AIツールは「社内文脈中心」に設計されている
Copilot のような社内生産性AIは、メール・文書・会議要約で力を発揮する。一方、CRM のケースを更新し、注文を処理し、商談を自律的に前進させるには、権限境界・監査ログ・顧客文脈データへのリアルタイム到達を備えた、別レイヤーの AI が必要だ。
盲点③：PoC が止まる本当の理由は「設計合意の不在」
日本企業の現場では、稟議文化・法務確認・情シス基準・SIer 役割分担のなかで PoC が立ち上がる。しかし PoC が本番化に届かない構造的原因は、技術力ではなく 本番化条件・KPI・データ整備計画が事前に合意されていないことにある。これは社内生産性AIより顧客接点AIで強く現れる。

ここまでの整理を一行で言うとこうなる。Copilot のような社内生産性AIは、メール・文書・会議要約で力を発揮する。一方、顧客業務を実行するAIは別レイヤーで設計する必要がある。次章では、Microsoft 365 / Copilot が「強い領域」と「設計目的が異なる領域」を整理する。

Chapter 02

Microsoft 365 / Copilotが強い領域、
構造上届きにくい領域

Microsoft 365 / Copilot を否定するのが本書の目的ではない。むしろ、強い領域を正しく認識することが、顧客接点AIの設計を考える出発点になる。

ここでは Microsoft 公式ドキュメントの記述に基づいて、Microsoft 365 / Copilot が 社内生産性AIとして強い領域を整理する。そのうえで、構造的に届きにくい領域は「Microsoft の弱み」ではなく 「設計目的が異なる」と位置づける。

Microsoft 365 / Copilot が強い領域

Microsoft Graph：社員業務文脈の統一API
Microsoft Graph は "emails, chats, documents, and meetings" を含む社員の業務文脈データへ統一API でアクセスできる2。Microsoft 365 Copilot はここを土台に、社員の日常業務を文脈化する4。
Copilot Studio：low-code エージェント構築
Copilot Studio は "graphical, low-code tool for building agents and agent flows"5。社内ワークフロー寄りのエージェントを業務部門が作りやすい設計で、すでに over 400,000 のカスタムエージェントが作成されている1。
Microsoft Fabric / OneLake：分析データレイク
OneLake は "single, unified, logical data lake for analytics data" として位置づけられ、Shortcuts で ADLS / S3 / Dataverse 等を参照できる6。BI・分析の中心的基盤として強力だ。
Microsoft Purview / Microsoft Entra ID
Microsoft Purview は M365 Copilot のデータセキュリティ／コンプライアンス制御を担い7、Microsoft Entra ID は ID／アクセス制御の前提として動作する8。社内側の AI 統制基盤として成熟している。
Teams / Outlook / Office との自然延長
すでに導入されている Teams / Outlook / Office との UI 連続性は、社員側の利用ハードルを大きく下げる。社内生産性AIとしての導入優位性は、他のどのレイヤーより明確だ。
Fortune 500 nearly 70% の利用
Microsoft 365 Copilot は Fortune 500 の nearly 70% で利用されている1（2025-03 時点）。社内生産性AI は、すでに「採用するか」ではなく「どう使い切るか」のフェーズに入っている。

構造上、別の設計が必要になる領域

ここから先は 「Microsoft の弱み」ではない。Microsoft 365 / Copilot がそもそも社内生産性領域に最適化されているからこそ、構造的に 別の設計が要る領域が存在する、という整理だ。

顧客接点業務のリアルタイム実行
取引フェーズ管理・ケース解決ワークフロー・与信判定・契約・同意管理は、CRM ネイティブの業務ロジックとして実装されている領域だ。Microsoft Graph の参照範囲とは設計目的が違う。これは優劣ではなく、レイヤーの違いとして捉えるのが妥当だ。
顧客接点 KPI への直接接続
一次解決率・商談化率・解約率・NPS・LTV といった顧客接点 KPIは、CRM の業務オブジェクト（ケース・商談・契約）と密に結びついている。社内文脈データだけでは、これらの KPI を AI に追わせることは設計上難しい。
顧客接点向けの権限境界とガバナンス
顧客データの権限モデル（CRM の OWD / 共有ルール / フィールド権限）、HitL（金融・医療・公共での人間承認）、監査ログ（AI のデータ参照履歴）は、社内ナレッジ向けのガバナンスと要件の粒度が違う。社内側で Microsoft Purview / Entra ID が担うのと同等の制御を、顧客データレイヤーでも別途設計する必要がある。
Microsoft 365 / Copilot は社内生産性AIの強力な基盤だ。
一方で、顧客接点AIには別の設計論が必要になる。
これは対立ではなく、レイヤーの違いを扱うための整理だ。
— 二層モデルで整理することの意味

この章で重要なのは、強みと届きにくさを「優劣」ではなく「役割の違い」として捉えることだ。次章では、顧客接点 AI の設計に必要な 5 つの設計原則を、製品名なしで整理する。

Chapter 03

顧客接点AIに必要な
5つの設計原則

「PoC は走るが本番化しない」を抜け出すには、設計の土俵を揃える必要がある。
本章では、製品名ではなく 5 つの設計原則として要件を整理する。

顧客接点 AI は、社内生産性 AI と違って 業務を実際に動かす。誤対応は解約・苦情・コンプライアンス違反に直結する。だからこそ、PoC の前に「これを満たさなければ本番に出さない」という設計原則を合意することが、PoC 倒れ回避の本質になる。

1
リアルタイム業務文脈
AI が判断・実行する瞬間に、商談・ケース・契約・購買・同意の最新状態が読めること。バッチ反映や夜間更新では、顧客対応の現場では遅すぎる。「いま、その顧客が、どのフェーズにいるか」を AI が即時に知れる構造が前提だ。
2
権限境界の保持
CRM の OWD（組織のデフォルト共有）／共有ルール／フィールド権限を、AI が逸脱せずに継承すること。「AI だから全部見える」は通らない。担当者の権限を超える顧客データを、AI が代理で参照・操作することは厳に避ける必要がある。
3
Human-in-the-loop（HitL）
金融・医療・公共・規制業種では、人間承認を介在させる発動条件を業務別に定義する。返金・与信・割引承認・契約変更など、リスクの高いアクションは AI が単独で完了させない。「いつ AI が止まり、誰が判断するか」を仕様として書き下ろす。
4
監査ログ・可説明性
AI の 判断プロセス・参照データ・実行アクションのログが、後から監査できる状態で残ること。法務・情シスからの「なぜこの判断をしたのか」「誰のデータを見たのか」に、ベンダ問い合わせなしで答えられる粒度が必要だ。
5
KPI 接続
AI の活動が 一次解決率・商談化率・解約率・NPS・LTVといった顧客接点 KPI に紐付いて測定できること。「便利になった気がする」では本番化の合意が取れない。PoC 開始前に、KPI と本番化条件をセットで合意する。

日本市場ならではの 4 つの確認ポイント

日本企業の現場では、上記 5 原則に加えて、いくつかの構造的な要因を織り込む必要がある。これらは「Microsoft か Salesforce か」というベンダ選定の話ではなく、設計プロセスを成立させるための前提条件だ。

稟議・法務・情シスの三者合意
AI が顧客データに触れる以上、稟議・法務確認・情シス基準の三者の合意が前提になる。PoC を始める前に、承認プロセスの全体像を関係部門で握っておくことで、本番化フェーズでの差し戻しを防ぐ。
SIer 役割分担の事前整理
社内 AI 担当 SIer と顧客接点 AI 担当 SIer が異なるケースは少なくない。役割分担と責任範囲を事前に整理しないと、本番化フェーズで「誰がどこまで」が曖昧になり、運用設計が止まる。
PoC 倒れの構造的回避
PoC が本番化しない原因の多くは、技術ではなく 本番化条件・KPI・データ整備計画の事前合意不在だ。「PoC で動いた」と「本番で運用できる」の間には、合意フォームの有無という溝がある。
顧客対応品質と人手不足
コンタクトセンター・カスタマーサクセスの人手不足が深刻化する一方で、日本企業の顧客対応品質への要求は高い。「省人化」と「品質維持」の両立を、設計原則として AI に組み込む必要がある。
本番化の判定基準
5 原則をすべて満たさない PoC は、本番に届かない。逆に言えば、PoC を始める前に「どの原則を、どのレベルで満たすか」を合意フォームに書き下ろせれば、PoC 倒れの大半は予防できる。

Chapter 04

顧客接点AIの成果を決めるデータ：
メール・文書ではなく、顧客文脈

顧客接点AIの精度は、モデルではなく データで決まる。
しかも必要なのはメール・文書のテキストではなく、商談・契約・購買・同意といった顧客文脈データだ。

GIGO（Garbage In, Garbage Out）——AI に対する古典的な原則は、顧客接点 AI でこそ効いてくる。どれだけ高性能なモデルでも、参照できるデータが社内文書・会議要約だけなら、顧客対応の業務は前に進まない。本章では、顧客接点 AI が必要とする 4 種の顧客文脈データを整理し、Microsoft Graph が扱うデータと並べて比較する。

顧客接点AIが必要とする 4 種のデータ

① 行動・履歴データ
商談履歴・ケース履歴・購買履歴・サポート履歴。「いつ、どの担当者が、どの顧客と、何を話したか」「どの商品をいつ買い、どの問い合わせで何を解決したか」が、時系列で揃っているか。
② 契約・与信・同意データ
契約条件・与信枠・マーケティング同意・Cookie 同意。AI がアクションを起こす際に「その顧客にこのアクションを取って良いか」を判断するための制約条件。同意違反はそのままコンプライアンス違反になる。
③ 対人関係データ
担当 SE・カスタマーサクセス・提案者の関与履歴。法人顧客では「誰がどの顧客とどう関わってきたか」が、提案・サポート品質の質を決める。組織内のリレーションも顧客文脈の一部だ。
④ チャネル横断データ
Web・店頭・コールセンター・メール・モバイルアプリ。顧客は1人だが、企業内では別チャネルとして分断されがち。同一顧客のチャネル横断ジャーニーを AI が見られるか。

Chapter 05 — 本書の中核章

Copilot for Sales / Sales Agent が示すこと：
AI 時代にも CRM データは重要である

Microsoft 自身が、Copilot の機能要件として CRM データへの到達を製品設計に組み込んでいる。
この事実こそ、「社内文脈の Graph」と「顧客接点文脈の CRM」が 両方必要であることの最も明確なエビデンスだ。

ここまでの章で、社内生産性 AI と顧客接点 AI の違い、5 つの設計原則、必要となる顧客文脈データを整理してきた。本章はそれらの抽象論ではなく、Microsoft 公式ドキュメントが示している事実から、二層モデルの妥当性を検証する。

事実 ①：Salesforce CRM Connector が CRM オブジェクトをインデックスする

"The Salesforce CRM Microsoft 365 Copilot connector enables your organization to index contacts, opportunities, leads, cases, and accounts objects in your Salesforce instance."
— Microsoft Learn: Salesforce CRM Microsoft 365 Copilot connector9

Microsoft 365 Copilot 自体が、社内の Microsoft Graph データだけでは完結せず、contacts / opportunities / leads / cases / accounts という顧客接点の主要オブジェクトをインデックスする Connector を公式に提供している9。これは技術的な選択肢ではなく、製品設計上の前提として組み込まれている。

事実 ②：Sales Agent は Dynamics 365 と Salesforce の両方に対応する

"The new Sales Agent for Copilot can automate workflows like turning your contacts into Sales Leads in either Dynamics or Salesforce."
— Microsoft 365 Blog (2025-03-05): New autonomous agents in Microsoft 365 Copilot1

Microsoft が新たに提供する Sales Agent for Microsoft 365 Copilotは、Dynamics 365 だけでなく Salesforce CRM へも書き込みを行う1。Microsoft 自身が 「自社 CRM だけでは顧客接点 AI は完結しない」という事実を、製品仕様で明確に認めているということだ。

この事実から読み解くべき、3 つの設計上の含意

含意 ①：Connector は読み取り中心 + 限定的書き込み
Connector のメインは contacts / opportunities / leads / cases / accounts のインデックス（読み取り）だ9。Sales Agent による Lead 化のような書き込みも一部あるが、CRM の業務ロジック全体を巻き取る設計ではない。
含意 ②：業務ロジックは CRM ネイティブ側に残る
取引フェーズ管理・ケース解決WF・与信・契約・割引承認・同意管理は、依然として CRM ネイティブの業務ロジックとして動く。Connector で読めるからといって、業務ロジックそのものが Copilot 側に移るわけではない。
含意 ③：社内文脈と顧客接点文脈は両方必要
Microsoft Graph（社内文脈）と CRM（顧客接点文脈）は、どちらか一方では完結しない。これは Microsoft vs Salesforce の対立ではなく、設計上の二層モデルとして整理されるべき関係だ。
本章のメッセージ
この二つの公式記述91から導かれる結論は明快だ。問題は「Microsoft か Salesforce か」ではなく、「どの AI を、どの業務レイヤーに置くか」だ。Copilot を全社展開した企業ほど、次に向き合うべき問いは「CRM データを AI が使える顧客文脈に変える設計」になる。

次章では、この二層モデルを支える基盤——データ基盤・業務基盤・ガバナンス基盤の 3 層を、両ベンダの公式表現で中立的に整理する。

Chapter 06

顧客業務をAIで動かすために必要な、
データ・業務・ガバナンスの基盤

二層モデルを実装するうえで、見落とされやすいのが「データ・業務・ガバナンスの3層構造」だ。
Microsoft 系・Salesforce 系それぞれの公式表現に基づいて、中立的に整理する。

本章は 3 つの基盤レイヤーに分けて整理する。①分析データレイク／顧客接点リアルタイム業務基盤、②業務ロジックの所在、③ガバナンス（ID・権限・監査）。それぞれで、Microsoft 系と Salesforce 系の役割を 公式記述ベースで並べる。優劣ではなく 役割分担として整理することが、両方を活かす設計の出発点になる。

① データ基盤：分析データレイク vs 顧客接点リアルタイム基盤

観点 OneLake / Microsoft Fabric Salesforce Data 360 のような顧客接点リアルタイム基盤
公式の位置づけ "single, unified, logical data lake for analytics data"6 "real-time data engine that powers the entire Salesforce platform"10
主な用途 分析・BI・データレイクハウス 顧客接点業務のリアルタイム実行
特徴 Shortcuts で ADLS / S3 / Dataverse を参照可能6 Zero Copy で Snowflake / Databricks / Google Cloud / AWS と連携10
業務との接続 分析結果は別系統で業務に反映 業務オブジェクト（ケース・商談・契約）と直接接続
役割の関係 置換ではなく 補完関係。OneLake のデータも Zero Copy 等で参照可能。
分析と業務実行は同じデータ基盤で兼ねにくい
分析用データレイクは「データの集約と分析」に最適化されている。顧客接点 AI が必要とするのは「業務状態のリアルタイム参照と書き込み」だ。要求される SLA・整合性・権限境界が違うため、同じレイヤーで兼ねさせないのが妥当な設計判断になる。

② 業務基盤：CRM ネイティブの業務ロジック

取引フェーズ管理・ケース解決ワークフロー・承認プロセス・与信判定・契約・割引承認・同意管理は、長年にわたり CRM ネイティブの業務ロジックとして実装されてきた。Ch5 で見たように、Microsoft 365 Copilot Salesforce Connector は これらを全部巻き取る設計にはなっていない9。これは制約ではなく、二層モデルの自然な帰結だ。

③ ガバナンス基盤：両ベンダの中立比較

観点 Microsoft 側 Salesforce 側
ID / アクセス制御 Microsoft Entra ID8 CRM 権限モデル（OWD / 共有ルール / フィールド権限）
データ統制 / コンプライアンス Microsoft Purview7 Einstein Trust Layer（Zero Data Retention 等）11
主な対象 社員業務文脈（M365 / Graph） 顧客接点文脈（CRM）
適用範囲 両方とも 必要。社内側と顧客接点側でそれぞれ統制設計が必要

想定される反論への返答（Q&A）

Microsoft Fabric / OneLake があれば、CRM のリアルタイム基盤は不要では？
役割が違う、というのが妥当な答えだ。OneLake は "single, unified, logical data lake for analytics data"6 として分析・BI に強い。一方、顧客接点 AI が必要とするのは「商談・ケースの最新状態をリアルタイムで読む／書く」業務基盤で、これは別レイヤーで設計するのが自然だ。OneLake のデータは Zero Copy で参照可能なため、置換ではなく補完として組み合わせるのが現実的な姿になる。
Teams が標準だから、別の現場連携 UI は不要では？
Teams が社員コラボレーションの標準であることは前提として、ここでの論点は別だ。顧客接点 AI の示唆を、現場の対応担当者が業務文脈の中で受け取る UIと、社員間コラボツールは設計目的が異なる。「Teams か別の UI か」ではなく、Teams は社員コラボに、顧客接点 AI の Agent UI は CRM データに紐付いた業務文脈に、それぞれ最適化されている、という役割分担として捉える方が実態に合う。
Microsoft 一体化のために、Dynamics 365 に寄せた方が運用は楽では？
既存の CRM 上に蓄積された データ・業務ロジック・カスタマイズ・権限モデルの規模次第で、移行コストは並行運用コストを大きく上回ることがある。さらに Ch5 で見たように、Microsoft 自身が Sales Agent を Dynamics と Salesforce 両対応に設計している1のは、両者の並行運用が現実的シナリオとして想定されているためだ。「寄せる」より、役割分担で並行運用を前提に設計する方が、リスクと投資の両面でバランスが良い場合が多い。

Microsoft 環境との共存パターン

Salesforce を顧客接点 AI レイヤーとして導入する際、Microsoft 環境を 置き換える必要はない。むしろ、Microsoft 公式が想定している共存パターンを活かすことで、両方の強みを引き出す設計が可能になる。

① Copilot for Sales / Sales Agent との接続
Microsoft 365 Copilot から Salesforce CRM へ contacts / opportunities / leads / cases / accounts を Connector でインデックス9。社員は M365 上で顧客文脈を参照し、業務実行は CRM 側で完結する。
② OneLake / Fabric から Zero Copy で参照
OneLake / Fabric 上の分析データを ETL なしで Data 360 から参照10。分析は Microsoft 側、業務リアルタイム実行は Salesforce 側、というレイヤー分担を維持できる。
③ Microsoft Entra ID + Einstein Trust Layer
ID 認証は Microsoft Entra ID8、データガバナンスは Microsoft Purview7と Salesforce Einstein Trust Layer11を併用。社内側・顧客接点側それぞれの統制を活かす。
